# Paquetes funcionales de EmonPlan

El agente principal de Codex lleva el recorrido del usuario de punta a punta. Preferir Astra como modelo principal cuando esté seleccionado en la sesión.

Para cada ronda y para el visto bueno de la ficha, aceptar respuestas por formulario o por chat. Al usar la herramienta asíncrona, mantener el turno abierto hasta recibir la respuesta del usuario. Usar esperas que se interrumpan al llegar un mensaje y renovarlas si siguen pendientes. Si el formulario desaparece, volver a presentar las preguntas pendientes con sus opciones. Solo una respuesta explícita permite avanzar.

1. **Entrevistar por rondas.** Leer AGENTS.md y el código afectado. Usar la herramienta de preguntas al usuario disponible (`request_user_input` en modo Plan o `request_user_input_async` en modo Default). Hacer varias rondas cortas y adaptar cada una a las respuestas. Cubrir quién usa la función, qué quiere lograr, el recorrido normal, los casos límite, qué queda fuera y qué evidencia demostraría que funciona. Ofrecer opciones concretas con sus consecuencias y dejar espacio para responder libremente. Resolver en el repo lo que se pueda comprobar y seguir preguntando mientras queden decisiones que cambien el resultado. Al cerrar la entrevista, Codex define una matriz de aceptación para el paquete. Para cada caso, especifica su identificador, precondiciones, datos de prueba, acción y resultado observable. Define pruebas unitarias para reglas y casos límite, pruebas de integración cuando la garantía depende de la API o PostgreSQL y escenarios Playwright para los recorridos de usuario que correspondan. Cubre el flujo principal, errores, límites y regresiones relevantes del alcance. Al revisar el recorrido actual, identificar las funciones existentes que el cambio podría romper e incluir cómo se comprobarán en su punto de uso.
2. **Mostrar la ficha HTML antes de implementar.** Generar y compartir un HTML autónomo, breve, accesible y fácil de abrir. Mostrar el objetivo, un ejemplo concreto con el antes y el después, el recorrido del usuario ilustrado paso a paso y cómo se implementará en las partes del sistema que correspondan. Incluir los límites acordados y un resumen de los criterios de éxito con sus verificaciones. Usar un diagrama, una maqueta o una tabla si ayudan a entender el cambio. Pedir el visto bueno mediante la herramienta de preguntas y esperar la respuesta. Si el usuario pide cambios, actualizar la ficha y volver a mostrarla.
3. **Implementar en Codex.** Con la ficha aprobada, el agente principal escribe y ejecuta la prueba de regresión, confirma que falla por el motivo esperado e implementa el cambio. Puede usar un subagente de Codex con un modelo más eficiente disponible para una tarea independiente con resultado verificable, si permite avanzar en paralelo y compensa el costo de transmitir contexto y revisar el resultado. En ese caso indicarle el alcance, los archivos que puede tocar, las convenciones de AGENTS.md y la evidencia esperada. El agente principal conserva la responsabilidad de integrar y verificar el recorrido completo.
4. **Revisar y cerrar.** Revisar el diff integrado y verificar la matriz con evidencia por identificador. Ejecutar las pruebas de backend y frontend, el build y el flujo real de Docker con los escenarios Playwright acordados. Corregir los fallos dentro del alcance. Consultar al usuario si resolver un hallazgo requiere una nueva decisión de producto. Informar cómo usar el resultado, las pruebas ejecutadas y cualquier criterio pendiente.

Para controles eléctricos, confirmar la fuente, edición, cláusula y alcance antes de implementar la regla. Si faltan, el paquete puede registrar el dato o marcar la revisión como pendiente.
